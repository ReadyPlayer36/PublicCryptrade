## Mutation-testing notes (honest corrections)
- An earlier rollback mutation result was invalid: it ran against a test folder that already contained failing placeholders, so "killed" was meaningless. It was redone against passing tests only.
- Valid findings: "commit on any failure" and "commit on integrity error" were NOT detected until failure-after-write tests were added (`test_failure_after_rows_are_written_rolls_everything_back_and_leaves_no_lock`, `test_integrity_error_after_rows_are_written_becomes_a_conflict_and_rolls_back`); both are now killed. The integrity-error path was also leaking the database error through `__context__`; it now raises outside the `except` block (verified by test and mutant).
- One equivalent mutant remains and is accepted: removing the explicit `connection.rollback()` in the generic failure path changes nothing observable, because closing the pooled connection rolls the open transaction back anyway. The explicit call is kept as belt and braces; D2 will assert that a ROLLBACK is actually issued.

## Known limits of this evidence
- The hollow-test scanner only checks that assertions exist; it cannot judge whether an assertion is strong. This map and mutation testing are the compensating controls.
- The transaction (TX-01/02/09), concurrency, metadata, service, legacy-scan, CLI and verification-SQL requirements are still placeholders (listed in `tests/hollow_allowlist.txt`) and are scheduled for Stages D2 and D3.
- None of this is independently executed evidence until the reviewer runs the suite and final gate.
